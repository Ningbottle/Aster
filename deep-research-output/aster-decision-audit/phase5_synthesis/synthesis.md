# Phase 5 — 综合分析与项目决策修订

日期：2026-08-16

## 综合结论

Aster 的方向合理，而且已经具备进入初始化和首个纵向切片的条件。真正的风险不在“Svelte + Tauri + Rust + SQLite + 子进程”这一技术链，而在三种容易被混淆的产品责任：宿主运行时管理、宿主交互连接、跨工具 Skills 证据。只要它们保持分层，Pi 与 DSH 不被压成一个 Agent 接口，Alpha 可以由一个开发者配合 coding agent 分阶段完成。

研究并不支持继续扩大常驻规则。`AGENTS.md` 应只保存少量、长期稳定、违反后代价高且无法由工具自动检查的不变量；产品范围、里程碑、估算、证据模型和开放问题进入 `content.md`。格式和机械质量要求进入 formatter、linter、schema 与测试。函数/文件行数只能触发审查，不能成为硬性正确性标准。

完整 Alpha 不等于一次性实现。RoadmapBench 所揭示的长周期集成失败，与当前项目十分接近：多目标任务往往只完成一部分。相反，纯 UI 假数据骨架又不能提前验证最危险的 Pi RPC、Windows 进程、GitHub 快照和回滚。因此第一条可运行链路应同时包含：一个真实 Pi 启动与最小 RPC 会话、一个真实 GitHub Skill 快照、一次部署、一条 evidence 和一次可验证回滚。

## 证据如何汇合

### 1. 约束文件：短、稳定、可验证

- [Evaluating AGENTS.md](https://arxiv.org/html/2602.11988) 未发现仓库 context file 对成功率的稳定显著提升，却观察到约 20%–23% 的额外成本。它不证明 context file 无用，而是反对自动生成或复制背景材料。
- [When Instructions Multiply](https://arxiv.org/html/2509.21051) 显示，即便附加指令互不冲突，“全部满足”的概率仍会随数量增加而下降；机械规则更适合程序验证。
- [Agent READMEs](https://arxiv.org/html/2511.12884) 发现真实 context files 倾向新增而很少删除。Aster 需要“替换/合并旧规则”的维护纪律，避免永久累积。
- [SkillsBench](https://arxiv.org/html/2602.12670) 最新 v4 的 87 个任务中，Skills 平均提高 16.6 个百分点，但 13 个任务为负向；1–3 个 Skill 的收益高于 4 个以上，综合型长文档表现很弱。这支持禁止整套 Superpowers 流程作为默认门禁，同时保留用户指定或任务确实需要的单个 Skill。

### 2. 产品澄清：问到足够就停止

- [ClarifyCodeBench](https://arxiv.org/html/2607.00711) 同时惩罚漏问和多问。当前高代价歧义已经解决：目标用户、平台、账号边界、宿主差异、更新责任、Skills 范围、数据与隐私均已确认。
- [SWE-RPG](https://arxiv.org/html/2608.09072) 表明需求恢复是独立瓶颈，但对计划允许不同文件、符号、架构和步骤顺序，只要责任等价。因此文档应固定“必须产生什么结果”，不给尚未验证的 trait、表结构或组件层级上锁。
- 从现在开始，只有会改变产品范围、安全责任、数据可逆性或公开承诺的问题才需要向用户追问；普通实现选择由开发者/Agent 通过小实验或 ADR 决定。

### 3. 双宿主：共享基础设施，不共享产品语义

- [SWE-agent](https://arxiv.org/html/2405.15793) 说明 ACI/工具表面本身会改变 Agent 行为。同一模型或相似任务不意味着不同 harness 可互换。
- Pi 与 DSH 可共享下载器、进程监管、日志脱敏、SQLite、文件快照和 EvidenceStore；它们不能共享 RPC 类型、消息状态机、插件/模式模型或对话 UI 流。
- Pi 只走 RPC；DSH 复用/嵌入其原生 Web UI 和插件/自定义模式。Aster 保持宿主特色，而不是装饰性重做。
- DSH 为 Developer Preview，Pi/DSH 上游都更新快速。HostProfile 只能描述发现和静态能力；深层操作由内置、版本门控的 Rust connector 执行。不支持版本时保留安全启动/停止/原生使用，暂停不兼容的深控制并标“未验证”。

### 4. Skills：管理快照与证据，不宣布通用兼容

- GitHub 是更新来源，不是身份要求。本地目录、离线导入、未知来源仍是合法来源状态。
- 原始 Skill 快照不可变、只读、不可执行；中文 Markdown 说明单独保存，用内容哈希关联，不污染上游内容。
- Aster 只部署精确副本，不默认创建 symlink/junction，不覆盖未托管目录。若托管目录被外部修改，先停止并展示 diff。
- `兼容` 不是布尔字段。Evidence 至少按 `snapshot × target host × host version × scope` 区分 discovered、downloaded、structurally_validated、configured、target_discovered、session_loaded、callable_verified；失败、未知、过期分别呈现。
- Pi/DSH 做深验证；Cursor、Zcode、Grok Build、Qoder、Codex、Claude Code、Zed、Kimi Code、Antigravity 在 Alpha 只承诺文件发现、部署和静态证据。缺少官方资料的目标显示低置信度，不由猜测填充。

### 5. 更新：一个入口，三个独立任务

- Aster、Pi、DSH 在每次应用进程首次进入时各检查一次更新；应缓存/节流，离线与失败不影响使用。
- 用户可逐个更新或点击“全部更新”，但后者只是调度三个独立任务，不是跨产品原子事务。
- 下载、验证、安装、切换各有证据。只有用户再次确认后才安装，不允许静默更新。
- Aster 只直接更新 Aster-managed 安装，或能够高置信识别且官方支持安全更新的安装。来源未知/手工修改的外部安装只提示或迁移，不覆盖。
- Aster-managed Pi/DSH 可以采用并排版本与活动指针：新版本先安装和验证，再切换并保留上一可用程序版本。但回滚承诺仅覆盖程序文件，不覆盖宿主自己产生的数据、插件状态或迁移。

## 对先前提问与结论的审计

| 先前假设或问法 | 问题 | 修订后的决定 |
|---|---|---|
| 先做完全 fake 的 Stage 0 骨架 | 只能证明窗口能开，不能验证最大的技术风险 | 保留基础设施初始化，但首个完成里程碑必须包含真实 Pi RPC 与一个真实 Skill 纵切 |
| 把完整 Alpha 当作一个开发任务 | 多目标、跨层、跨宿主，一次性交付的集成失败概率高 | Alpha 是产品范围；开发拆成 6 个可运行里程碑 |
| 讨论 Aster 账号或宿主凭据存储 | Aster 不需要账号域，会扩大安全责任 | Aster 无账号；模型/API 凭据始终归 Pi/DSH，Aster 只报告缺失状态 |
| 最初考虑不由 Aster 更新 Pi/DSH | 与用户核心需求矛盾 | 更新中心是 Alpha 核心，但安装显式确认，Aster/Pi/DSH 三个任务独立 |
| 把并排安装等同完整回滚 | 宿主数据迁移和外部包管理器不可由 Aster可靠撤销 | 只承诺 Aster-managed 程序位回滚，界面明确数据兼容风险 |
| “全部更新”暗示共同事务 | 三个上游没有共同一致性边界 | “全部”仅是队列动作，每个结果独立呈现 |
| 每次进入都实时阻塞检查更新 | 网络抖动会破坏本地优先体验 | 每个进程首次进入检查一次，缓存/节流，失败非阻塞，可手动重试 |
| 所有 HostProfile 可远程动态更新 | 数据规则也可能改变安全行为，增加供应链面 | Alpha 随 Aster 发行内置、只读、不可执行 profile；签名数据包留待以后评估 |
| 11 个工具都做深兼容 | 缺少稳定官方信息且测试矩阵过大 | Pi/DSH 深证据；其余只做文件级能力，置信度与未知显式展示 |
| 所有 Skill 都必须有 GitHub 地址 | 用户已有本地下载，来源可能未知或离线 | GitHub 是可选 update provider；本地来源是一等状态 |
| 批量部署可以做数据库式事务回滚 | 多个独立宿主目录、文件锁、杀毒软件会使真正 ACID 不成立 | 使用部署计划、逐步日志、原子文件替换与补偿回滚；逐目标报告结果 |
| 诊断包完全删除路径信息 | 会损失定位多工作区、冲突目录问题所需结构 | 默认令牌化/伪匿名路径，预览后导出；仍排除用户名、原文对话、工作区内容和凭据 |
| 固定每个函数/文件的最大行数 | 行数不能代理职责清晰度，还会增加无意义拆分 | 仅作 review trigger：约 60–80 行函数、400–600 行手写文件需检查，但不自动判失败 |
| 持续逐题确认实现细节 | 已越过高价值澄清点，继续会拖延并污染上下文 | 访谈在产品边界确认后结束；余下选择由实验、测试和 ADR 决定 |
| 为 Pi 与 DSH 建统一接口和统一对话流 | 会抹掉 harness 的 ACI、插件、模式和持久化差异 | 只共享平台服务；产品连接器和界面流程独立 |
| AppData\\Local 承担全部长期备份 | 本地数据不天然具备漫游/备份保障 | Alpha 仍按已确认决定使用 `AppData\\Local\\Aster`；把导入/导出作为明确备份路径，后续再评估 Roaming |

## 推荐 Alpha 交付序列与粗估

估算面向一个熟悉 TypeScript/Rust/Windows 的开发者，使用 coding agent 辅助；这是范围规划区间，不是发布日期。外部上游变化、代码签名、Windows 安全软件和 DSH 破坏性升级会显著影响周期。

| 里程碑 | 可运行结果 | 预计 |
|---|---|---:|
| M0 基础 | Svelte 5/Tauri 2/Rust/SQLite 可启动；数据目录、迁移、进程监管、日志脱敏、Evidence 核心与测试 fixture | 1–2 周 |
| M1 Pi + Skill 窄纵切 | 真实 Pi 发现/启动、最小 RPC 会话与流事件；一个 GitHub Skill 快照、验证、测试范围部署、evidence、回滚 | 2–3 周 |
| M2 DSH 纵切 | DSH 发现/启动/停止，原生 Web UI，插件/模式保持可用，版本门控和降级状态 | 2–4 周 |
| M3 Skills Manager 广度 | 仓库分组、GitHub 更新/设备授权、中文说明、扫描、11 目标 profile、批量部署计划、静态与深证据 | 3–5 周 |
| M4 更新与恢复 | Aster/Pi/DSH 独立检查，managed 并排版本，确认安装、切换、程序位回滚；会话恢复、导入/导出、诊断包 | 2–4 周 |
| M5 Alpha 硬化 | Windows 10 22H2/11 x64 矩阵，路径/重解析点/文件锁/杀软竞态、安装器与签名、可访问性、文档 | 2–4 周 |

合计粗估 12–22 周，置信度中低。范围可并行，但 Pi/DSH 的官方变化可能使连接器返工；不应把压缩日期转化成减少验证或静默覆盖用户安装。

## 文档落地原则

根 `AGENTS.md`：只写不可变边界、工作方式、安全和完成定义；不复制路线图，不固定实现形状，不要求完整 Superpowers 流程。

根 `content.md`：作为当前产品/架构事实源，包含范围、责任边界、证据状态、更新语义、数据与隐私、里程碑、风险和验收标准。产品决定变化时，先更新该文档；高代价技术偏离另写 ADR。
