# Phase 2：Aster 决策审计的证据版图

日期：2026-08-16｜数据库：45 条记录

## 研究问题

1. 哪些访谈问题属于不可逆产品决策，值得写入长期规范？
2. 哪些问题只是实现偏好，过早确定会削弱开发 Agent 的判断？
3. 如何让较大的 Alpha 范围仍可被可靠交付？
4. `AGENTS.md` 如何提供高价值上下文而不形成“约束堆栈”？
5. 宿主更新、回退和安全承诺应该怎样写才不超出 Aster 能控制的边界？

## 主题一：需求澄清与隐含需求

SWE-RPG 与 ClarifyCodeBench 把“会写代码”和“会发现需求歧义”区分开。它们支持在开发前澄清高代价歧义，但不支持无限提问。更好的问题选择标准是：答案是否会改变数据所有权、不可逆架构、安全边界、用户流程或验收证据。

对访谈的判断：关于 Pi/DSH 是否统一、是否管理凭据、是否覆盖 unmanaged 目录、是否静默更新，这些问题必要；关于某些可逆目录形状、页面细节和尚无实现证据的内部机制，不应逐项让用户批准。

## 主题二：Context files 与多约束遵循

AGENTS.md 实证研究与多指令基准共同指向一个稳健结论：更多规则不等于更高成功率。Context files 的价值主要来自准确的构建/测试命令、架构事实、局部约定和安全边界。重复 PRD、主观代码风格、固定函数行数以及流程 Skill 强制链会增加冲突与认知负担。

因此 `AGENTS.md` 应短于产品文档，并通过链接指向 `content.md`。行数只可作为 review 信号；完成标准应落在行为、测试、错误处理和可恢复性。

## 主题三：长周期 Agent 开发与纵向切片

RoadmapBench、SWE-bench 以及交互式 Agent 基准显示，多文件长周期工作仍不稳定。纯骨架无法验证关键技术风险，而整个 Alpha 一次性交付又会放大规格漂移。最合适的中间结构是：范围上定义完整 Alpha，执行上拆为独立可运行的纵向里程碑。

推荐的首个纵切不是 fake-only：真实启动一个受支持的 Pi、完成最小 RPC 会话、导入一个真实 GitHub Skill snapshot、部署到测试 scope、产生 evidence 并回退。DSH 和跨工具扩展随后加入。

## 主题四：Skills、宿主差异与证据

Skills 研究、工具检索研究和 SWE-agent 都表明宿主/harness 是能力的一部分。“已下载”“已部署”“宿主已发现”“会话已加载”“已验证可调用”必须分离。中文说明面向用户理解，但不是兼容声明，也不能替换上游正文。

这部分支持既有的 `HostProfile + HostConnector + EvidenceStore`，同时反对在 `AGENTS.md` 枚举每个平台的全部规则。动态规则放版本化 profile，运行事实进 evidence。

## 主题五：更新、恢复与安全承诺

安全论文支持不可变快照、最小权限、显式批准和确定性检查，但不能证明任意第三方安装都可回退。需要严格区分：

- Aster-managed runtime：可使用版本并存与 active pointer，验证后切换。
- recognized external runtime：只有官方机制明确支持时才能代为更新。
- unmanaged/unknown runtime：只提示或迁移，不覆盖。
- Aster 数据库迁移：必须备份并测试 downgrade/restore 路径，但不承诺新版本宿主产生的会话数据一定能被旧宿主读取。

## 主题六：声明配置与专用实现

软件架构与插件可变性研究支持把静态变化点声明化，但运行时行为、进程协议、权限和验证不能被数据文件伪装。第一阶段不开放任意可执行 Connector 插件仍然合理。

## 对访谈问题的分级

### 应成为不变量

- Windows x64 首发；本地优先；无 Aster 账号与模型凭据域。
- Pi 和 DSH 是独立产品表面，不统一对话流。
- Pi 只通过 RPC 连接；DSH 保留原生特性和界面。
- 原始 Skill snapshot 不可变；中文说明独立；Aster 不执行 Skill 脚本。
- unmanaged 目录不覆盖；写操作可恢复；状态由 evidence 产生。
- 禁止整套 Superpowers 流程成为项目门禁，个别适用 Skill 可按请求使用。

### 应成为当前产品决定，但允许 ADR 修订

- Aster-managed Pi/DSH 的安装与更新中心。
- 版本并存、验证后切换、保留上一可用版本。
- HostProfile 第一阶段随 Aster 发布。
- AppData 存储、无便携模式、导入导出。
- 启动后首次进入检查更新，禁止静默安装。

### 不应写成硬约束

- 固定函数/文件行数。
- 具体 Rust trait、Svelte store 或数据库表名。
- “所有批量操作都能跨产品原子回滚”。
- “任意 Pi/DSH 版本都能被 Aster 安装或回退”。
- 视觉布局、导航细节和内部目录树永久不变。
- 每个开发任务都必须先走同一套 planning/TDD/review Skill 流程。

## Phase 2 结论

总体产品方向没有被研究推翻，真正需要修正的是约束表达和交付分解。最终文档必须维护一张“事实/决策/假设/非目标”边界，并给 Alpha 配置可验证里程碑，而不是再增加访谈问题。
